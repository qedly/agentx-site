Start with a task
you can review.

A focused bug fix, a small improvement, or a missing test. Give Rovara a clear request and use the returned change to decide what comes next.

01 / Fix

“Fix the CSV export bug.”

Describe the failure and the expected behavior. Inspect the patch and the available checks before accepting it.

02 / Improve

“Add pagination to this endpoint.”

Delegate a bounded change while you work elsewhere. Follow up in the same workspace when you want an adjustment.

03 / Test

“Add coverage for this edge case.”

Ask for a concrete test. Review what it exercises and read its output alongside the code.

What is in the evidence?

Open a sample explanation. These examples describe the report format, not the result of a live task.

Test output

ILLUSTRATIVE REPORT · NO LIVE RUN SHOWN

Inspect the command and its output, rather than relying on the agent’s summary. A real task reports the checks it could run.

Command
npm test -- tests/export.test.ts
Output
The test’s output would appear here. This illustration makes no claim that the test has passed.
What to inspect
The named test, its exit outcome, and any failures or timeouts.

A passing command is evidence about that run. Your review and repository CI still matter.

Check report

ILLUSTRATIVE REPORT · NO LIVE RUN SHOWN

The check report separates the agent’s claim from the checks the runtime ran.

Check source
Project-configured checks, or recognized test commands from the coding session.
Before / after
Where a baseline is available, compare whether the check passed before the change and what happened after it.
Outcome
Passed, failed, timed out, or not rerun. A run without usable checks is marked not verified.
Next step
Inspect failures, ask for a follow-up, or review the pull request. You decide what gets merged.

Check output is reported evidence. It is not a guarantee that the code is correct.
