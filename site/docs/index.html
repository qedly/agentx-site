AgentX/Field guide

01 — OVERVIEW

A coding task gets a place to stay.

AgentX is a source-available coding-agent runtime. A task started in a Slack thread or handed over from an MCP-compatible coding tool gets a separate remote workspace. The workspace runs on an EC2 worker in your AWS account and uses encrypted EBS storage so its files and conversation state can remain available when idle compute stops.

AgentX is an executor and workflow surface. It does not replace source control, CI/CD, identity, cloud, or release authority. A person remains responsible for reviewing and merging the resulting pull request.

Release and license

There is no published AgentX release or npm package yet. Current source is licensed under FSL-1.1-ALv2: source-available, not an OSI-approved open-source license. Each release converts to Apache 2.0 two years after it ships.

Slack ingress queues the request for the hosted Pi orchestrator. AgentX services allocate or resume the task workspace; the remote Pi worker runs the coding session and approved GitHub tools. MCP callers use the developer task API. This is the documented architecture, not a guarantee of any particular live deployment state.

WHEN IDLE

Compute can stop while the task's encrypted workspace volume and conversation remain available to resume.

03 — FIRST TASK PATH

The finish line is one useful reply in Slack.

A complete setup deploys the AWS environment, connects GitHub and Slack, configures developer sign-in and a project, and confirms AgentX replies in a project channel. Treat this as a platform setup, not a local demo.

  1. A dedicated AWS accountFirst setup needs administrator credentials. Environments in a shared AWS account are not security boundaries from each other.
  2. Node.js 22.19 or newerThe current source-checkout installer builds locally. AWS CloudShell's default Node 20 is too old.
  3. GitHub App ownershipA GitHub organization or personal account creates the app and chooses repository access.
  4. Slack app permissionYou need a Slack workspace where you can create and install apps. A workspace administrator may need to approve the app.
  5. Model accessAmazon Bedrock is the default; Anthropic, OpenAI, or OpenRouter can also be configured. Model charges are separate from AWS charges.
  6. Region and quota capacityCurrent release material lists us-east-1. The installer checks worker capacity and two free Elastic IPs for the NAT gateways.
No npx install yet

There is no published package to install. The source-checkout path requires repository access, a locally built release, and worker/Slack images that you build and push to a registry. Follow the install and release guides in your authorized AgentX checkout; details may change before publication.

05 — CONNECTIONS

Slack is an entry point, not the whole product.

Use Slack when a task belongs in a team conversation. Use MCP when a developer wants Claude Code, Codex, or Cursor to hand a task to a remote AgentX worker. The AgentX MCP server exposes tools to list allowed projects, start/check/continue/share/cancel/close tasks, and open pull requests.

Project setup can add Linear, Jira, Asana, or any remote MCP server as connectors. That project context is separate from the MCP interface developers use to start or manage an AgentX task.

WHERE IT FITS

Slack gives the team a shared thread. MCP lets an individual coding workflow delegate. Neither changes AWS ownership or who merges the code.

06 — TRUST BOUNDARIES

Clear boundaries are product facts, not a security certification.

  • Each task has its own EC2 worker and encrypted EBS workspace.
  • The first installer run needs AWS administrator credentials. It creates a narrower operator role for later day-two commands.
  • Installer secrets are entered through hidden prompts, files, or environment variables and stored in AWS Secrets Manager; they are not stored in local AgentX settings.
  • Environments in the same AWS account do not form a security boundary from each other. Use separate accounts where a separate boundary is needed.
  • The coding worker can read and edit checked-out repositories and run shell commands in its workspace. Treat model and worker output as untrusted until review.
  • AgentX does not replace GitHub permissions, CI rules, identity providers, AWS guardrails, or human merge authority.

Review the current architecture and release documentation in the authorized source checkout before deploying to a production account. This page is a product explanation, not a penetration test, compliance report, or security attestation.

07 — EVALUATION

No solve rate until the comparison is fair.

AgentX has SWE-bench evaluation tooling and a small internal pilot. The pilot is useful engineering evidence, but it does not support a public solve-rate or model-comparison claim: runs used different worker images during the session and surfaced result-reporting and verification issues. The current campaign specification is still a draft.

The draft campaign calls for pinned runner images, matched tasks, repeats, and cost per solved task. The team should publish the method, task set, image digest, model configuration, run outcomes, and known limitations together. Until that controlled evaluation is complete and independently checked, AgentX makes no public SWE-bench performance claim.

Slack test material stays private

Slack is a working task surface, but private messages, names, and run screenshots should not appear on the public site without a consented and redacted demonstration. A public demo should use a test repository and show one reproducible path from request to reviewable result.

08 — READINESS

What is not ready today.

  • No public AgentX source repository, release, or npm installer is available.
  • Current release documentation lists us-east-1 as the supported region.
  • Administrative tools for coding assistants to read AgentX state or make confirmed admin changes are not built yet.
  • The SWE-bench model comparison campaign is not complete; no public score is ready.
  • No public customer adoption, time-saved, quality-improvement, or production-outcome evidence is published here.

We will update this page with the public source, exact release commit, install path, support matrix, and evaluation record before changing the readiness statement.
