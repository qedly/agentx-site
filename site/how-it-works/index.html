How Rovara works

The work. The evidence. Your call.

Hand over a coding task. Follow the work in a persistent workspace. Inspect the change and its evidence before your team decides what gets merged.

01 / The workflow

A complete coding workflow.

Rovara runs a coding agent, carries the task through its workspace, and returns work for you to inspect. The checks support that workflow.

REQUESTSlack or MCP

A task in an allowed project.

WORKRemote coding agent

EC2 workspace in your account.

INSPECTChange + evidence

Check output and missing checks.

REVIEWYour team

You decide what gets merged.

  1. Give it a task.

    Start in Slack or use your coding tool’s MCP connection. Choose an allowed project and describe the change you want.

  2. The remote agent works.

    It reads and edits the project, runs shell commands, and works in a persistent workspace in your AWS account.

  3. Inspect the changes and evidence.

    Read the diff, the check output, and what could not be checked. Ask for a follow-up if the task needs more work.

  4. Review a pull request.

    Request a pull request when you are ready to review the change in GitHub. Your team decides whether to merge it.

02 / Evidence

Read the check, not just the claim.

When the coding session finishes, the runtime reruns configured project checks when available. Otherwise, it can rerun recognized test commands from the session. It compares before and after where a baseline is available.

If a check that passed before now fails, the agent gets one extra attempt. The final report still shows unresolved failures. A stopped run, an error, or a task without usable checks can be marked not verified.

What passed

The named command passed in that run. Review whether it covers the task you asked for.

What failed or regressed

Inspect the failing command and its output. A failure is not hidden by the agent saying the task is done.

What could not be checked

Missing or unrerun checks stay visible. They are not treated as a pass.

Evidence for your review.

Checks provide evidence about the commands that ran. They do not prove the code is correct or replace your repository’s CI and review rules.

03 / Follow up

Keep the workspace. Continue the task.

Ask for another change without starting from a blank workspace. Task files and conversation state persist when idle compute stops; a follow-up can resume the task.

Retained storage still costs money. Closing a workspace is a separate lifecycle action; inspect the operator guidance before cleanup.

04 / Architecture

Your account is the boundary.

Your team deploys and operates the AWS environment. Slack ingress and a Fargate orchestrator route tasks to isolated EC2 workers with encrypted EBS workspaces. Developer MCP calls enter through the task API.

The first install needs administrator access. Separate environments inside one AWS account are not independent security boundaries. Use separate accounts where you need a separate boundary.

Model requests leave the account for the configured provider. GitHub and Slack have their own permissions and data flows. “Your AWS account” describes infrastructure ownership; it does not mean every external connection stays inside AWS.

05 / Human authority

You decide what gets merged.

The workflow ends with work your team can review. You choose whether to request changes, continue the task, or merge a pull request using your repository’s existing controls.

In the current reporting-enabled publication path, a draft pull request can include failing checks so you can inspect the code and the failures. Older compatible paths can refuse publication when readiness checks fail. Configured CodeBuild checks report evidence; they are not an automatic merge gate.

The runtime has no GitHub merge operation. That is how the workflow keeps final merge authority with your team.
